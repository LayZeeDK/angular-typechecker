# Phase 05.1 Learnings: 0.0.2 First OIDC Steady-State Publish Verification

## Decisions

### Decouple the local release cut from push (release.git.push:false + createRelease:false)
`nx.json` `release.git.push: false` plus `changelog.workspaceChangelog.createRelease: false`,
so `nx release --skip-publish` cuts the version commit + changelog + tag entirely LOCALLY.

**Rationale:** `createRelease: "github"` forces a git push (it must push the tag to tie the
Release to it), which defeated a "cut locally, curate, then push" flow. Decoupling makes
curation always precede the push.
**Source:** 05.1-01-SUMMARY.md, nx.json, 38b7fbf

### Keep registry-url in setup-node (do NOT drop it)
`actions/setup-node` `registry-url: https://registry.npmjs.org/` is RETAINED.

**Rationale:** registry-url is what makes npm DETECT the OIDC trusted-publishing environment;
removing it yields `ENEEDAUTH`. npm >= 11.5.1 runs the OIDC handshake first and ignores the
empty/placeholder `_authToken`.
**Source:** 05.1-01-SUMMARY.md, release.yml cd656f5

### The GitHub Release is created locally, not in CI
With `createRelease:false`, the maintainer runs `gh release create ... --notes-file <curated>`.

**Rationale:** keeps the CI publish job at `id-token: write` only (never `contents: write`),
preserving the hardened least-privilege posture (D-13); the Release uses the curated changelog.
**Source:** 05.1-01-SUMMARY.md, 05.1-SECURITY.md

### The live publish stays human-gated (B-01); the agent never publishes
The `npm-publish` GitHub Environment required-reviewer approval gates the only irreversible step.

**Rationale:** an npm version is immutable and cannot be unpublished/republished; only a human
approves the deployment. The autonomous chain stops at "ready to approve".
**Source:** 05.1-01-PLAN.md, 05.1-VERIFICATION.md

### AGENTS.md changes must be code-reviewed
A repo policy requiring every AGENTS.md change to pass a code review (satisfiable by the
mandatory code_review_gate).

**Rationale:** AGENTS.md governs all agent behavior; an unverified instruction propagates
silently. The deep review immediately caught a factual inaccuracy (WR-01), validating the policy.
**Source:** AGENTS.md, 05.1-REVIEW.md

## Lessons

### npm Trusted Publisher must be actually SAVED -- a simultaneous "Publishing access" edit blocks it
The repeated 0.0.2 publish 404s were NOT a workflow bug: the Trusted Publisher was never saved
at 05-05 because the package's *Publishing access* setting was changed in the same npmjs.com
save. Since 0.0.1 used a token, the TP was never exercised until 0.0.2 exposed it.

**Context:** npm does not validate TP config on save; the misleading `404 PUT .../<pkg>` means
the TP does not match / was never saved -- check it first on any OIDC 404.
**Source:** 05.1-01-SUMMARY.md, 05.1-VERIFICATION.md

### "Drop registry-url on 404" was WRONG guidance for npm >= 11.5.1
The ROADMAP/inline D-04 contingency said to drop registry-url if OIDC 404s. Doing so caused
`ENEEDAUTH` (npm never attempted OIDC). registry-url is REQUIRED for OIDC detection.

**Context:** a documented "fix" that made things worse; corrected in release.yml comments,
AGENTS.md, SUMMARY, ROADMAP, and project memory.
**Source:** 05.1-01-SUMMARY.md, 05.1-REVIEW.md

### createRelease forces push; --skip-publish does not suppress it; explicit push:false hard-errors
`createRelease:"github"` + `git.push` at DEFAULT -> nx flips push to true -> silent push of the
version commit + tag during the local step (gated by `changelog.git.push`, not `skipPublish`).
`createRelease` + EXPLICIT `git.push:false` -> nx HARD-ERRORS (`GIT_PUSH_FALSE_WITH_CREATE_RELEASE`,
process.exit), it does not silently push.

**Context:** the deep review (WR-01) corrected the AGENTS.md landmine that conflated these two
nx 23.0.1 behaviors; verified against `command-line/release/config/config.js`.
**Source:** 05.1-REVIEW.md (WR-01), AGENTS.md d2aec48

### conventionalCommits derives NO bump when only docs/chore commits exist -> pin a literal version
12 commits since the 0.0.1 tag were all docs/chore, none touching the package -> `nx release`
with `conventionalCommits` computes no bump. 0.0.2 had to be pinned with a literal positional
(`nx release 0.0.2 --skip-publish`), which also bypasses the 0.x adjustment deterministically.

**Context:** the release-mechanics memory's "auto-bumps to 0.0.2" was the pre-tag state and was
stale; verified against the live commit log.
**Source:** 05.1-RESEARCH.md, 05.1-CONTEXT.md (D-01)

### npm `_npmUser` is the decisive proof of a tokenless OIDC publish
`npm view <pkg>@<ver> --json` -> `_npmUser: "GitHub Actions <npm-oidc-no-reply@github.com>"` is
written ONLY for an OIDC Trusted-Publisher publish; a token publish shows the human npm user.

**Context:** this single field objectively closed the OIDC steady-state verification (the one
fact the code review could not self-verify -- IN-03).
**Source:** 05.1-VERIFICATION.md

### Branch rulesets block force-push even for the owner; the gh token cannot toggle rulesets
The "v0.0.1" branch ruleset blocked force-push to main; the `gh` token (scopes gist/read:org/
repo/workflow) returns 404 on the rulesets PATCH (lacks repo-admin). Toggling required the
maintainer in the UI. The "Release tag" ruleset had a User-`always` bypass, so the tag could be
force-moved with the maintainer's credentials without disabling it.

**Context:** plan force-push-based reconciliations around the actual ruleset + token capabilities;
managing rulesets via API needs a fine-grained PAT with "Repository rules: write".
**Source:** 05.1-01-SUMMARY.md

### A backgrounded session loses the live Agent() handle, but executor work is durable in git
When the session was backgrounded mid-execution, the orchestrator never received the executor's
checkpoint signal -- it "disappeared." But each task commits atomically, so Tasks 1-2 (version
cut + tag + PKG-05) were intact in git, paused cleanly at the B-01 human gate.

**Context:** recover via filesystem + git state (the documented completion-signal fallback), not
the lost signal; never re-run a paused-at-checkpoint plan from scratch.
**Source:** 05.1-01-SUMMARY.md, 05.1-STATE recovery episode

## Patterns

### Local-first hardened release flow
`nx release <ver> --skip-publish` (push:false) -> curate CHANGELOG + amend -> `git push origin
<tag>` -> human approves the `npm-publish` environment (OIDC publish) -> `gh release create
--notes-file <curated section>`.

**When to use:** any hardened, human-gated npm release where the public changelog must be curated
and the CI publish job must stay `id-token: write`-only.
**Source:** AGENTS.md gotcha #3, 05.1-01-SUMMARY.md

### Regression-lock hard-won config invariants in the release-hygiene spec
Add durable assertions for invariants a phase *proved the hard way*: registry-url RETAINED;
`git.push:false` + `createRelease:false`. Skip non-durable pins (e.g. a literal version that
changes every release).

**When to use:** after debugging a config trap, encode the corrected invariant as a test so the
wrong "fix" cannot be re-applied silently.
**Source:** 05.1-VALIDATION.md, release-hygiene.int.spec.ts (15/15)

### Reconcile a force-push-protected main via temporary ruleset disable
Maintainer disables the blocking branch ruleset in the UI -> `git push --force-with-lease` main +
force-move the tag (Release-tag User bypass) -> maintainer re-enables the ruleset. The agent does
the pushes; the human owns the ruleset toggle and the irreversible publish.

**When to use:** when an un-curated/wrong commit + tag was pushed to a protected branch and must be
cleanly erased before a real publish. Prefer fixing the upstream cause (here: push:false) so it
never recurs.
**Source:** 05.1-01-SUMMARY.md

### Diagnose a misleading npm OIDC 404 by the failure shape
404 *with* registry-url = OIDC attempted but the entity was not authorized (TP mismatch / not
saved). `ENEEDAUTH` *without* registry-url = OIDC never attempted (no registry config). Both point
away from the workflow YAML and toward the Trusted Publisher config + npm/Node version.

**When to use:** any npm trusted-publishing failure; check npm>=11.5.1/Node>=22.14, id-token:write,
and the exact-match (and *saved*) TP before touching the workflow.
**Source:** 05.1-01-SUMMARY.md, deep-research findings

## Surprises

### The first OIDC publish failed twice with two different misleading errors before the real cause surfaced
404 (with registry-url) then ENEEDAUTH (without), neither naming the actual problem.

**Impact:** several publish cycles + a wrong-turn registry-url removal before the root cause (TP
never saved) was found; npm's trusted-publishing errors are notoriously misleading (npm/cli#9088).
**Source:** 05.1-01-SUMMARY.md

### `nx release --skip-publish` pushed to origin
Against the "local cut" expectation, the unified command pushed the version commit + tag (via
`createRelease:"github"`).

**Impact:** an un-curated commit + tag landed on a force-push-protected main, requiring a temporary
ruleset disable to undo; root-caused and fixed with `git.push:false` + `createRelease:false`.
**Source:** 05.1-01-SUMMARY.md

### A documented contingency was itself wrong
The repo's own ROADMAP/inline "drop registry-url on 404" advice (D-04) was the wrong fix and made
the failure worse (ENEEDAUTH).

**Impact:** a debugging detour; reinforced that documented "fixes" must be verified against current
tool behavior (npm >= 11.5.1) -- corrected across docs + memory + added a regression test.
**Source:** 05.1-01-SUMMARY.md, 05.1-REVIEW.md

### The always-auth warning was benign and from setup-node, not the repo
`npm warn Unknown user config "always-auth"` came from setup-node@v5's generated .npmrc, not any
committed config; it persisted across the registry-url toggle and did not affect the publish.

**Impact:** minor; fixed for future releases with a guarded `sed` strip step after setup-node;
not worth chasing via experimental registry reconfiguration.
**Source:** 05.1-01-SUMMARY.md, release.yml 6a21be0
