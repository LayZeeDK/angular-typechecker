## Summary

Phase 5.1 cuts `angular-typechecker@0.0.2` and proves the tokenless OIDC steady-state
npm publish works end-to-end. 0.0.1 was seed-published with a one-time granular token
(npm cannot do a first publish via OIDC -- npm/cli#8544), the npm Trusted Publisher was
registered, and the seed token revoked. The OIDC path is therefore REGISTERED but never
EXERCISED. 0.0.2 is the first release that authenticates tokenlessly. The mechanism is
fully built: `release.yml` is already the documented WORKING OIDC config and `nx.json`'s
release block is correct. This phase is operational verification, not new construction.

The work splits cleanly into a small set of AUTONOMOUS preparation/verification tasks
(re-confirm pre-flight invariants, run a non-destructive `nx release --dry-run`, cut the
version+changelog+tag locally with `--skip-publish`, curate `CHANGELOG.md`, prepare the
push) and a HUMAN-GATED irreversible action (approve the `npm-publish` GitHub Environment;
the maintainer alone performs the publish per B-01). The single empirical question this
phase answers: does `setup-node`'s `registry-url` write an empty `_authToken` into
`.npmrc` (because `NODE_AUTH_TOKEN` is unset) that defeats OIDC and yields a misleading
404? Current (2025/2026) npm docs + tracking issues confirm that with npm >= 11.5.1 / Node

> = 22.14.0 (already met: Node 24 + `npm i -g npm@latest`) the OIDC detection runs BEFORE
> any token fallback, so the as-is config SHOULD succeed. The documented REACTIVE remedy if
> it 404s on auth is to drop `registry-url` from the `setup-node` step and re-run (safe: a
> 404-on-auth means nothing was published, and `nx release publish` is idempotent -- it
> `npm view`s the version first).

**Primary recommendation:** Attempt the publish with `release.yml` AS-IS (D-03). Cut 0.0.2
with an EXPLICIT literal version (`npx nx release 0.0.2 --skip-publish`, NOT `--first-release`,
preview with `--dry-run` first), hand-curate the changelog, push the tag, STOP at the
`npm-publish` approval gate for the human (B-01). Verify success via `npm view
angular-typechecker@0.0.2 --json` (version + SLSA provenance + dist-tag latest) + a GitHub
Release. Keep `release.yml` OIDC-only and the `release-hygiene` spec green as the regression
guard. Apply the `registry-url` drop ONLY if it 404s.

## The OIDC / registry-url / empty-\_authToken Mechanics (the verification crux)

This is the single empirical question 0.0.2 answers. Below is the precise mechanism, the
current-docs decision, and the exact reactive remediation.

### How the failure mode works

1. `actions/setup-node` with `registry-url: https://registry.npmjs.org/` writes a project
   `.npmrc` that contains BOTH the registry line AND a line referencing the auth-token env
   var, roughly:
   ```
   registry=https://registry.npmjs.org/
   //registry.npmjs.org/:_authToken=${NODE_AUTH_TOKEN}
   ```
   [CITED: github.com/actions/setup-node/issues/1440] The `_authToken=${NODE_AUTH_TOKEN}`
   line is injected by setup-node regardless of whether the token env var is set.
2. If `NODE_AUTH_TOKEN` is UNSET, that line resolves to an EMPTY `_authToken=`. On OLDER npm
   (< 11.5.1), npm may treat the empty token as "a token is present" and short-circuit the
   OIDC detection -- the handshake never runs, npm is treated as anonymous, and the registry
   returns a misleading 404 (anonymous cannot PUT). [CITED: github.com/npm/cli/issues/9088 --
   "misleading 404 / ENEEDAUTH instead of trusted-publishing diagnostics"]
3. On npm >= 11.5.1, the CLI detects the OIDC environment and uses it for authentication
   BEFORE any token fallback, so the empty `_authToken` does not interfere. [CITED:
   docs.npmjs.com/trusted-publishers; multiple 2025/2026 postmortems corroborate the
   "upgrade to npm 11.5.1 / Node 24 fixed it instantly" outcome].

### Why `registry-url` must STAY (do not proactively drop it)

`setup-node`'s `registry-url` is REQUIRED for OIDC to work -- it writes the `registry=`
line into `.npmrc` so the CLI knows which registry to run the OIDC handshake against. The
problem is NOT `registry-url` itself; it is the empty-`_authToken` line setup-node pairs
with it on OLD npm. With npm >= 11.5.1 the pairing is harmless. [CITED:
docs.npmjs.com/trusted-publishers shows `registry-url` in the canonical OIDC example.]

### The decision (crisp)

- **DEFAULT (D-03): attempt AS-IS.** release.yml already meets BOTH conditions that make the
  empty-`_authToken` line harmless: npm >= 11.5.1 (release.yml:56 `npm i -g npm@latest`) and
  Node 24 (release.yml:54). The as-is publish SHOULD succeed. This is the empirical claim 5.1
  validates.
- **REACTIVE ONLY (D-04): if it 404s on auth, drop `registry-url`.** Dropping `registry-url`
  removes the empty-`_authToken` line entirely; the CLI then relies purely on OIDC env
  detection. This is the inline release.yml remediation. It is SAFE to re-run: a 404-on-auth
  means nothing was published, and `nx release publish` runs `npm view` on the target version
  before publishing, so re-running the same 0.0.2 is idempotent (no version conflict). [CITED:
  nx.dev/docs/guides/nx-release/release-npm-packages -- "uses npm view to look up the current
  version before publishing ... run the same publish action multiple times without negative
  side-effects".]

### IMPORTANT regression interaction if D-04 is applied

If the reactive drop is needed, the executor edits `release.yml` (removes the
`registry-url:` line from the `setup-node` step). That edit MUST keep ALL `release-hygiene`
invariants green (it does NOT touch any asserted invariant -- the spec asserts SHA-pinning,
`persist-credentials: false`, `contents: read`, `id-token: write`, an environment, provenance
on, and NODE_AUTH_TOKEN unset; `registry-url` is NOT asserted). After any release.yml edit,
re-run `npx nx run angular-typechecker-install-e2e:test` (or the targeted spec) to confirm
the gate stays green (D-09). Note: dropping `registry-url` is a code change to a tracked file
and must be committed + pushed (the running workflow reads the committed file at the pushed
ref).

**What:** Pass the exact version as a positional to `nx release`; bypasses conventional-commits
derivation AND the 0.x shift-down.
**When to use:** Releasing in a window with zero releasable (`feat`/`fix`) commits (this phase).
**Example:**


**What:** SLSA provenance attaches via `id-token: write` + `NPM_CONFIG_PROVENANCE: true`,
regardless of whether auth is a token (0.0.1 seed) or OIDC (0.0.2).
**When to use:** Reasoning about why 0.0.1 already has provenance even though it used a token.
[CITED: docs.npmjs.com/trusted-publishers; 05-05-SUMMARY.]

### Anti-Patterns to Avoid

- **Re-adding `NODE_AUTH_TOKEN` (even empty) to "fix" a 404.** An empty value BREAKS OIDC; a
  real one is unnecessary and re-introduces a standing-secret leak vector. The fix is the
  `registry-url` drop, not a token. [CITED: github.com/npm/cli/issues/9088; release.yml:72-76.]
- **Using `--first-release` for 0.0.2.** It tells nx NOT to expect existing tags/changelog --
  wrong now (they exist). Omit it. [CITED: nx.dev -- "after the first release, --first-release
  will no longer be required".]
- **Relying on conventional-commits to compute the bump.** Zero releasable commits -> no bump.
  Pin the literal (D-01).
- **Shipping the auto-generated changelog.** It is empty or leaks internal scopes -- curate by
  hand (D-06, AGENTS.md gotcha #2).
- **The autonomous chain performing the publish.** B-01: the chain STOPS at "ready to approve";
  the human approves the `npm-publish` environment. The publish is irreversible (immutable npm
  version). [CITED: 05-05-PLAN.md GATE; D-10.]
- **Pushing release tags by hand outside `nx release`.** [CITED: AGENTS.md gotcha #3.]

## Common Pitfalls

### Pitfall 1: The misleading OIDC 404 (the empty-\_authToken trap)

**What goes wrong:** The publish step fails with a 404 (or ENEEDAUTH) that looks like "package
not found" but is actually an auth failure -- OIDC never engaged.
**Why it happens:** setup-node's `registry-url` writes `_authToken=${NODE_AUTH_TOKEN}` into
`.npmrc`; with `NODE_AUTH_TOKEN` unset it resolves to empty, and OLD npm short-circuits OIDC
detection. [CITED: npm/cli#9088, actions/setup-node#1440]
**How to avoid:** npm >= 11.5.1 + Node 24 (ALREADY in release.yml). If it still 404s, drop
`registry-url` from setup-node (D-04), commit+push, re-fire (idempotent).
**Warning signs:** A 404/ENEEDAUTH on the `nx release publish` step despite a correct TP config;
the run log showing the CLI treating itself as anonymous.

### Pitfall 2: conventional-commits computes NO bump -> nx release "does nothing"

**What goes wrong:** Running bare `npx nx release` reports no releasable change (or prompts);
no 0.0.2 is produced.
**Why it happens:** All commits since the tag are `docs`/`chore` and none touch the package;
with `conventionalCommits: true` + project-scoped attribution, there is no bump. [VERIFIED:
git log + diff --name-only since the tag, 2026-06-28.]
**How to avoid:** Pass the LITERAL version: `npx nx release 0.0.2 --skip-publish` (D-01).
**Warning signs:** Dry-run output showing "no changes" or version unchanged at 0.0.1.

### Pitfall 3: Re-tagging conflict on a re-fire

**What goes wrong:** After a 404-and-fix, re-running locally errors because the
`angular-typechecker@0.0.2` tag already exists.
**Why it happens:** The local `nx release` already created the tag; only the CI publish failed.
**How to avoid:** Do NOT re-run `nx release` locally on a re-fire. The fix is a release.yml
edit (drop registry-url) + push; then re-trigger the SAME existing tag's workflow (re-run the
failed job, or `workflow_dispatch`). `nx release publish` is idempotent on the version. If a
fresh tag is unavoidable, delete the local+remote tag first, but prefer re-running the workflow.
**Warning signs:** `fatal: tag 'angular-typechecker@0.0.2' already exists`.

### Pitfall 4: Curated changelog vs nx-generated changelog drift

**What goes wrong:** The auto-generated CHANGELOG/Release leaks `docs(05):`-style scopes or is
empty; or the hand-curated entry is overwritten by a later `nx release` run.
**Why it happens:** nx renders the commit scope; with only docs/chore commits the generated
section is empty/noisy. [CITED: AGENTS.md gotcha #2.]
**How to avoid:** Run `nx release ... --skip-publish` to produce the version+tag, then hand-edit
CHANGELOG.md to the curated 0.0.2 entry (0.0.1 style), stage `CHANGELOG.md` by name, and commit
(amend or a follow-up commit) BEFORE pushing the tag. The GitHub Release notes (createRelease:
github) derive from the changelog, so curate before the tag push.
**Warning signs:** A 0.0.2 CHANGELOG entry containing `(05.1-...)` scopes or `[#N]` refs, or an
empty entry.

### Pitfall 5: ASCII / contact-email slips in public artifacts

**What goes wrong:** An em-dash, emoji, or the work email lands in CHANGELOG.md or the Release.
**Why it happens:** Default model output uses Unicode punctuation; the work email is in the
session context.
**How to avoid:** ASCII-only; `larsbrinknielsen@gmail.com` only. The `release-hygiene` spec
asserts the public email presence in SECURITY.md (not the changelog) -- but the constraint is
repo-wide.
**Warning signs:** mojibake in the rendered changelog; `consensus.dk` anywhere in tracked files.
