## Warnings

### WR-01: `discover` step does NOT fail loud on a script error (contradicts the stated invariant)

**File:** `.github/workflows/ci.yml:168`

```yaml
- id: list
  run: echo "projects=$(node tools/ci/list-e2e-projects.mjs)" >> "$GITHUB_OUTPUT"
```

**Issue:** The design (review brief + the ci.yml comment at 178-179: "real CI
always uses the discover-job output", fallback is "ONLY for `act -n`") assumes that
if the script throws, "the job fails loud". It does not. GitHub's default step
shell is `bash --noprofile --norc -eo pipefail {0}`, but a command substitution
that fails INSIDE an argument to `echo` does not trip `set -e` -- `echo` itself
exits 0. Verified empirically:

```
$ set -eo pipefail; echo "projects=$(node -e 'process.exit(1)')" > f; echo $?
0                      # step "succeeds"
$ cat f
projects=              # empty value written to $GITHUB_OUTPUT
```

Consequence: when `list-e2e-projects.mjs` throws (malformed `project.json`, a script
bug, an ambient-node incompatibility), the `discover` job goes GREEN with
`projects=` empty, and in REAL CI `fromJSON(needs.discover.outputs.projects || '[...]')`
falls back to the hardcoded 4-project list -- exactly the silent fallback the
comment claims happens "only under act". A discovery failure is thus masked
(mis-attributed to the `test` job's guards, which DO catch the same error via
`enumerateE2eProjects` / the execSync consistency `it`, so `ci` still ultimately
goes red -- this is why it is WARNING not BLOCKER).

**Fix:** split the substitution into a standalone assignment so `set -e` catches a
non-zero script (verified: the assignment form exits 1 and aborts):

```yaml
- id: list
  run: |
    projects=$(node tools/ci/list-e2e-projects.mjs)
    echo "projects=$projects" >> "$GITHUB_OUTPUT"
```

Then update the ci.yml comment at 178-179 so it no longer claims the fallback is
act-only / that real CI "always" uses the discover output -- with the fix, a script
throw fails the `discover` job outright (loud, correctly attributed), and the
fallback truly only serves `act -n`'s empty output.

### IN-01: the script's filter diverges from `enumerateE2eProjects`; they coincide only via a separate invariant

**File:** `tools/ci/list-e2e-projects.mjs:34` and `packages/angular-typechecker/src/ci-e2e-coverage-guard.spec.ts:44-55`

**Issue:** `listE2eProjects` pushes a name only when `projectJson.targets?.e2e` is
defined, whereas `enumerateE2eProjects` maps EVERY `e2e/*` directory to its name
with no `targets.e2e` filter. The new consistency `it`
(`discovered.toEqual(enumerateE2eProjects(...))`) passes today only because
GUARD-01's first `it` separately enforces that every `e2e/*` project defines an
`e2e` target (verified: all 4 current projects do). If that invariant is ever
broken, the consistency `it` fails for a reason unrelated to the script's own
correctness -- the script would still be behaving correctly (matrix should not
include a project without an `e2e` target), yet the test conflates that with a
script drift. This is fail-SAFE (it can only ever false-RED, never false-GREEN), so
it is informational, but the "mirrors GUARD-01's enumerateE2eProjects" claim in the
script header (line 3-4) is not literally true.

**Fix (optional):** either add the same `targets?.e2e` filter to
`enumerateE2eProjects` so the two are genuinely equivalent, or soften the header
comment to note the script intentionally restricts to `e2e`-target projects
(the CI-matrix-correct set) while GUARD-01 separately guarantees that equals the
full `e2e/*` set. Also note (minor, shared by both functions): both call
`readFileSync(.../project.json)` unconditionally for every directory under `e2e/`,
so a non-project directory there throws ENOENT in both -- acceptable as fail-loud,
but worth knowing before someone adds a shared `e2e/<helpers>` dir.

## Info

### LB-IN-01: cache key busts across ALL cells on any single fixture change (speed-only, harmless)

**File:** `.github/workflows/ci.yml:257`

**Issue:** The primary key's `hashFiles(...)` segment globs the fixtures of EVERY
e2e project (`e2e/**/fixtures/**/...`), not just the current cell's project. So a
lockfile/manifest change in one cell's fixtures invalidates the primary key for
ALL cells simultaneously (only the `${{ matrix.project }}` segment differs between
cells; the hash segment is identical across them). Effect: slightly more cache
misses than strictly necessary -- an unrelated cell rebuilds its warm Verdaccio
storage after a neighbour's fixture edit.

This is fail-SAFE and speed-only: the broad `restore-keys` prefix
(`verdaccio-storage-${{ runner.os }}-${{ matrix.project }}-`, line 259) still
restores the cell's most recent cache on a primary-key miss, and Verdaccio simply
re-fetches any delta (fidelity is independent of the cache per item 5). It matches
nub's deliberate "favor a loose key / high restore-hit-rate" philosophy, so no
change is required. Optional tightening (only if a future measurement shows the
cross-cell bust materially hurts the hit rate): scope the hash to the cell, e.g.
add per-project fixture globbing -- but this is not worth the added key complexity
for a speed-only, already-measured-marginal lever.
