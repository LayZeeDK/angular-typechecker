# Quick Task 260715-050 -- RESEARCH-3: GitHub-native Nx remote cache (feasibility + CREEP + scoping)

**Researched:** 2026-07-15
**Domain:** Nx 23 remote caching, GitHub Actions cache security (CVE-2025-36852 / CREEP), CI supply-chain posture
**Confidence:** HIGH on the contract + CREEP mechanism; MEDIUM on the cross-matrix correctness landmine (nx hashing) and the effort estimate.

## Verdict (read first)

1. **Feasible without new secrets/scopes: YES.** Nx 23 has a first-class, free "build your own caching server" contract (OpenAPI, since Nx 20.8). A GitHub-Actions-Cache-backed store rides on `ACTIONS_CACHE_URL` + `ACTIONS_RUNTIME_TOKEN` (auto-injected, NOT the `permissions:` block) -- **zero new long-lived secret, zero new permission scope.** [CITED: nx.dev self-hosted-caching]
2. **CREEP is mitigable to LOW residual risk for THIS repo -- the user need NOT simply "accept" it.** The decisive mitigations are structural and already half-present: this repo triggers on `pull_request` (NOT `pull_request_target`), so untrusted PRs write only to the isolated merge-ref cache scope that `main`/tags cannot restore; and the release build is cache-miss-by-design (release.yml never sets the cache env var). See section 4.
3. **Best GitHub-native backend: GitHub Actions Cache** (via `@actions/cache`), because it is the only option whose native branch-scoping maps directly onto the CREEP trust boundary AND needs no new secret/scope. See section 3.
4. **BUT the measured payoff is small and carries a correctness landmine, so: make it its OWN (low-priority, optional) GSD phase AFTER the e2e split -- do NOT fold it into the current e2e task, and do NOT block the split on it.** The 43% e2e win is already banked by parallelism and is independent of any cache. See sections 6-7.

## 1. The Nx 23 remote-cache contract (the thing the raw `.nx/cache` copy is NOT)

Confirmed: a **remote** cache is a fundamentally different, portable, cross-runner mechanism -- unlike the raw `upload/download-artifact` of `.nx/cache`, which nx rejects as machine-specific (`unknown-local-cache`, per MEASUREMENTS.md). [CITED: nx.dev self-hosted-caching]

- Since **Nx 20.8** you implement a tiny HTTP server against a fixed **OpenAPI spec**. Two endpoints only, keyed by nx **task hash**, transferring the task's output tar as `application/octet-stream`:
  - `PUT /v1/cache/{hash}` -- upload a task output. Bearer auth. **Must return `409` if the key already exists** (immutability -- load-bearing for CREEP, see section 4).
  - `GET /v1/cache/{hash}` -- download a task output. Bearer auth. `404` on miss.
- Nx is pointed at the server with **`NX_SELF_HOSTED_REMOTE_CACHE_SERVER`** (+ `NX_SELF_HOSTED_REMOTE_CACHE_ACCESS_TOKEN`, optional `NODE_TLS_REJECT_UNAUTHORIZED=0`). A workflow-local server is the intended pattern: `export NX_SELF_HOSTED_REMOTE_CACHE_SERVER="http://localhost:3000"`. [CITED: nx.dev self-hosted-caching; nrwl/nx Discussion #30548]
- The cached artifact = **task outputs + terminal output**, keyed by the task's input hash (source files + external dep versions + declared inputs). It is content-addressed by hash, so a build done once on runner A is genuinely replayed on runner B when the hash matches -- **portable by design.** [CITED: emilyxiong.medium.com]

**Provenance note:** the spec calls the payload "a tar archive as binary data" and warns "the underlying data format may change in future Nx versions" -- so the server is a dumb blob store keyed by hash; it must NOT try to parse the tar.

## 2. Deprecation landscape (what's free vs paid in Nx 23)

Timeline (community -> paid -> free -> deprecated) [CITED: emilyxiong.medium.com; nx.dev deprecated/self-hosted-cache-packages]:

| Era | State |
|-----|-------|
| Pre-Nx 20 | Community `tasksRunnerOptions` plugins (e.g. `@nx-aws-plugin/nx-aws-cache`, `NiklasPor/nx-remotecache-custom`). All archived. |
| Nx 20 (Sep 2024) | `tasksRunnerOptions` deprecated; caching went DB-driven; self-hosting required **paid Nx Powerpack (~$250/seat/yr)**. |
| Nx 20.8 (Apr 2025) | **Free official self-hosted plugins reintroduced** + the OpenAPI "build your own" RFC. |
| **2026-05-21** | `@nx/s3-cache`, `@nx/gcs-cache`, `@nx/azure-cache`, `@nx/shared-fs-cache` **all DEPRECATED due to CREEP** (design flaw, unpatchable). Stay on npm, no patches. |

**What replaced them in Nx 23:**
- **Nx Cloud** (recommended; has a free tier; NOT affected by CREEP due to its hierarchical/branch-scoped architecture). *Flag per constraints:* Nx Cloud needs an external service + an access token -- it would break the tokenless-OIDC posture and is therefore **out of scope for this repo** unless the free tier's token model is separately vetted.
- **Powerpack conformance/owners folded into paid Nx Enterprise.** [CITED: nx.dev self-hosted-caching]
- **"Build your own" against the OpenAPI spec remains first-class and FREE.** This is the only in-scope path. The four deprecated `@nx/*-cache` packages are dead ends -- do not use them (`@nx/azure-cache` is the deprecated example the user linked). [CITED: nx.dev deprecated/self-hosted-cache-packages]
- Community `nx-remotecache-custom` (NiklasPor) is **archived and does not work on Nx 21+** -- not viable. [CITED: emilyxiong.medium.com]

## 3. GitHub-native backend options, ranked

The workflow-local-server pattern: a ~50-line Hono/Express (or a pinned third-party action) listening on `localhost`, translating `PUT/GET /v1/cache/{hash}` onto a GitHub-native blob store, started before `nx` runs.

| Rank | Backend | New secret/scope? | CREEP trust-boundary fit | Limits | Verdict |
|------|---------|-------------------|--------------------------|--------|---------|
| **1** | **GitHub Actions Cache** (`@actions/cache`, via `ACTIONS_CACHE_URL`/`ACTIONS_RUNTIME_TOKEN`) | **None** (runtime token, not `permissions:`) | **Best** -- native branch/merge-ref scoping isolates PR writes from `main` (section 4) | ~10 GB/repo ceiling with LRU eviction; 7-day idle TTL | **Recommended** |
| 2 | GitHub build artifacts (`actions/upload-artifact`) | None | Poor -- no content-addressing by hash, no branch-scoped read isolation; you'd re-implement scoping | 90-day retention; not designed as a KV store | Rejected |
| 3 | Git LFS | Needs write to LFS store; pollutes git history | Poor -- no per-hash TTL, no branch scoping | LFS bandwidth/storage quotas | Rejected |
| 4 | Container registry (ghcr.io) | **Needs `packages: write`** (new scope, violates constraint) | Weak; heavier | OCI push/pull overhead | Rejected |

**Existing OSS glue (prior art):**
- **`raegen/nx`** [VERIFIED: github.com/raegen/nx] -- a GitHub Action that runs the nx CLI with remote cache backed by `@actions/cache`. **Closest direct match.** Caveats: only ~11 stars, ships a committed `dist/` bundle (audit-heavy), and it takes over nx invocation while holding `ACTIONS_RUNTIME_TOKEN`. If adopted: SHA-pin + Dependabot like every other action here; but a self-owned ~50-line server is easier to audit and trust than a low-star third-party action in the cache-write critical path.
- Standalone servers (`IKatsuba/nx-cache-server` 35*, `nxcite/nx-cache-server` Rust, `enxtur/nx-caching-server` Go) all target **S3/GCS/Azure and require a persistently-hosted server** -- they do NOT fit the "no new infra, GitHub-native" constraint. [VERIFIED: gh search]
- `falcondev-oss/github-actions-cache-server` is a drop-in for the GH cache API for *self-hosted runners* -- adjacent, not applicable (this repo uses GitHub-hosted runners).

**Recommendation:** if pursued, prefer a **self-owned tiny localhost server over `@actions/cache`** (own the code, no third-party trust in the token path), or adopt `raegen/nx` SHA-pinned if the maintenance saving outweighs the audit burden.

## 4. CREEP (CVE-2025-36852) -- mechanism + mitigations rated for THIS repo

**Mechanism (severity 9.4, "first-to-cache-wins" race)** [CITED: nx.dev creep blog; nx.dev deprecated/self-hosted-cache-packages]:
The attacker opens a PR off `main` with **no source changes but a modified CI workflow** that builds a malicious artifact. The workflow definition is **not part of the nx cache key**, so the PR hashes to the **same key `main` will hash to**. If the PR **uploads its poisoned artifact first**, every later trusted build with that key gets a **cache hit on the poison and ships it without rebuilding**. Checksums match (poison happens *before* hashing), so encryption/access-control/signing do not help. The bucket-based `@nx/*-cache` plugins were fatally exposed because a **single credential reads+writes the whole cache with no branch binding.**

**Why a GitHub-Actions-Cache-backed store is structurally different (the crux):** GitHub Actions cache is **branch/merge-ref-scoped**, not a single flat bucket [CITED: docs.github.com dependency-caching; github.blog 2026-06-26]:
- A run can restore caches from **its own ref + the default branch only**.
- A `pull_request`-triggered run writes to the **merge ref (`refs/pull/N/merge`) scope**, which **`main` and other PRs CANNOT restore** -- it is restorable only by re-runs of that same PR.
- `pull_request` and `release` **keep read-write** cache (non-default-branch scope); the 2026-06-26 read-only change targets only default-branch-SHA-context untrusted triggers (`pull_request_target`, `issue_comment`, fork `workflow_run`).

So the CREEP write-into-a-scope-that-trusted-workflows-read path is **closed by construction** for this repo, provided the glue uses `@actions/cache` (which respects the run's scope via the runtime token).

**Mitigations, rated for angular-typechecker:**

| # | Mitigation | Applies here? | Rating |
|---|-----------|---------------|--------|
| i | GitHub's 2026-06-26 **read-only cache for untrusted triggers** | Defense-in-depth; this repo doesn't even use the affected triggers | HIGH (free, automatic) |
| ii | **Use `pull_request`, NOT `pull_request_target`** | **Already the posture** (ci.yml line 25). Fork PRs run in fork context (no base-cache write); same-repo PRs write merge-ref scope | **DECISIVE -- already satisfied** |
| iii | **Write cache only from trusted contexts** (`push` to main, tags); PRs read-only or PR-scoped | Native GH scoping already delivers this; can be belt-and-suspenders enforced by gating writes on `github.event_name == 'push'` | HIGH |
| iv | **Exclude the publishable/release build from cache replay** | release.yml does NOT set `NX_SELF_HOSTED_REMOTE_CACHE_SERVER` -> published artifact ALWAYS freshly built | **DECISIVE (see section 5)** |
| v | **409-immutability** on existing keys | `@actions/cache` is naturally write-once per key (a second save of an existing key is a no-op) -> maps to the required 409 | HIGH (spec-mandated) |
| vi | Integrity/signing of entries | Not needed given ii+iv; the release path bypasses cache entirely | LOW priority |

**Residual-risk conclusion:** with (ii)+(iv) -- both structural and (ii) already true -- residual CREEP risk for this public repo is **LOW and acceptable.** The nx docs' caution ("self-hosting means accepting full responsibility for the threat model") is real, but the responsibility here is satisfied by trigger choice + scope isolation + release-path exclusion, not by ongoing vigilance. The user does **not** need to "accept CREEP" as an unmitigated risk.

## 5. Release-provenance interaction (the clean split)

The bytes npm-publishes (with OIDC provenance) must **never** be a replayed cache entry -- otherwise a poisoned cache entry becomes a supply-chain compromise of the published package. This is the SLSA principle: *"the output of the build must be identical whether or not the cache is used; one build must not inject false entries into a cache used by another."* [CITED: SLSA via GitHub cache-poisoning research]

**This is already the case and requires zero new work:** `release.yml` runs `npx nx build angular-typechecker` on a fresh checkout and **does not set the remote-cache env var**, so the release build is a **cache-miss-by-design** -- always fresh. A remote cache added to `ci.yml` (PR/push feedback) is cleanly walled off from `release.yml` (trusted publish). Keep it that way: **never introduce `NX_SELF_HOSTED_REMOTE_CACHE_SERVER` into release.yml.** This cleanly separates "fast feedback" from "trusted release."

## 6. The correctness landmine (decisive for value, MEDIUM confidence)

The 6-cell test matrix exists to catch **OS/Node-specific** regressions. **By default nx does NOT include OS or Node version in the task hash** (only source, lockfile dep versions, and declared inputs). So `nx test`/`nx typecheck` on `ubuntu/node22` and `windows/node26` with identical source hash to the **same key** -> a remote cache would let one cell **replay another cell's result**, turning the matrix into theater (6 green cells, 1 real execution). For a type-checking tool whose entire value is correctness, that is unacceptable.

- **Mitigation:** add `RUNNER_OS` + the Node major as `env` **named inputs** in `nx.json` so each cell's hash is distinct. [CITED: emilyxiong.medium.com -- env named inputs]
- **But that collapses the payoff:** with distinct per-cell keys, there are **zero within-run cross-cell hits**; only **cross-run** hits survive, and those fire only when a target's inputs are unchanged yet the path gate did NOT already skip the job -- a narrow window for a small repo.
- Similarly, the heavy `e2e` targets (~580s of the tier) have external side effects (Verdaccio, tarball installs, network) and should remain non-cacheable, so the dominant cost is **not** safely cache-eligible anyway.

**Net measured value (from MEASUREMENTS.md):** the only safe, genuine within-run cross-runner hit is the e2e build handoff (`angular-typechecker:build`, Linux/node24 build job -> Linux/node24 e2e cells) = **~2-4s/cell x 4 = ~8-16s**, for standing up an entire security-sensitive cache. Low.

## 7. Scoping recommendation

**Make it its own OPTIONAL, low-priority GSD phase, AFTER the e2e split -- do not fold it into the current e2e task.**

Reasons:
- **Independence:** the per-project e2e split already delivers ~43% (267s) via parallelism and needs **no cache** (per-cell rebuild is only ~2-4s). The split can and should land first, on its own. There is no "before" dependency to justify.
- **It is workspace-wide infra with a security model.** A remote cache touches the whole workspace and carries a real threat model (CREEP). That is exactly the shape GSD's **secure-phase gate** + a dedicated threat model + its own tests are for -- it does not belong bolted onto an e2e wall-clock task.
- **Low, landmine-adjacent payoff.** Given section 6, the honest expected value is small and easy to get subtly wrong (matrix masking). A separate phase lets it be justified by a broader workspace-wide need (or dropped) rather than rushed.

**Rough effort if pursued (separate phase):** MEDIUM. ~50-line localhost Hono server over `@actions/cache` (or SHA-pinned `raegen/nx`), a `build` job that writes the cache on `push`/tags, PR jobs that read, `RUNNER_OS`+Node env named inputs in `nx.json` (correctness), a threat-model doc, and guard tests asserting (a) release.yml never sets the cache env var, (b) writes gated to trusted contexts, (c) 409-immutability behavior. Plus a throwaway-PR measurement to confirm the hit rate is worth the surface area.

**vs the RESEARCH-2 alternatives:** the remote cache does NOT beat the already-measured per-project split for the e2e tier (the split is faster, simpler, and cache-independent). Its only unique offering is cross-run workspace-wide hits, which sections 6 shows are marginal here. **Recommend: ship the split now; treat the GH-native remote cache as a deferred, optional experiment, not a requirement.**
