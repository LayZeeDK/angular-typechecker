## Important

### WR-01: A mechanism is asserted as **PROVEN** when only the outcome was observed -- the section's own standard forbids this

**File:** `AGENTS.md:279-289`

> **An `analysis_key` change ALONE does NOT orphan the config -- PROVEN, and it is why the
> category must be preserved across a setup migration.** ... **GitHub RE-HOMED the
> configuration**: probe PR #70 ... passed the `CodeQL` tool check cleanly.

**What is wrong.** "Probe #70 passed" is an observation. "GitHub re-homed the configuration
**because** the migration kept `category` byte-identical" is an unobserved causal mechanism,
and the paragraph then leans on that mechanism to tell future maintainers they can skip step
0 ("keep the category byte-identical and you will not need step 0 for CodeQL at all").
Nothing in the evidence isolates `category` as the causal variable.

**At least two alternative mechanisms fit the same evidence and are not excluded:**

1. **Disabling default setup is what retired the old configuration.** Item 7(b) records that
   default setup was set to `not-configured` before the advanced workflow first ran. GitHub
   knows that producer is gone, so it has no reason to keep expecting its configuration --
   regardless of category. Under this mechanism the mitigation is "disable the old setup",
   NOT "preserve the category", and the advice in the new text is right for the wrong reason.
   Critically, this mechanism has no analogue for a third-party tool: there is no "disable"
   signal when you rename a workflow or job, which is exactly the case the generalised rule
   invites (see WR-02).
2. **The expected-configuration set tracks the most recent analysis per (tool, category) on
   the base ref.** The newest analyses for both categories on `main` are the advanced ones,
   so the old tuples simply stop being expected. This also fits the earlier CATEGORY-rename
   orphan (a renamed category leaves an old category whose newest analysis can never be
   refreshed) -- and it means category preservation matters, but for a reason the text does
   not state.

The section holds itself to precisely this discipline 70 lines further down
(`AGENTS.md:348-352`): *"The EFFECT is proven (maintainer PRs #64/#65 got both checks;
Dependabot PRs #46/#59 got neither); the REASON is INFERENCE"*. Step 0 should not get a
weaker standard than item 6.

**Fix:** keep the outcome bolded, demote the mechanism.

```markdown
   **An analysis-key change did NOT orphan the config here -- OUTCOME PROVEN, MECHANISM
   INFERRED.** The 2026-07-25 CodeQL default -> advanced migration changed `analysis_key`
   (`dynamic/github-code-scanning/codeql:analyze` -> `.github/workflows/codeql.yml:analyze`)
   AND `environment`, while deliberately keeping `category` byte-identical
   (`/language:actions`, `/language:javascript-typescript`). OBSERVED: probe PR #70, run with
   CodeQL required again and with all 126 historical default-setup analyses still present on
   `main`, passed the `CodeQL` tool check cleanly. No deletion was needed and none was done --
   an earlier draft of this runbook claimed a setup migration orphans the config, and that
   claim is disproved. WHY it passed is INFERENCE, and at least three explanations fit:
   GitHub re-homed the configuration because the category was preserved; OR disabling default
   setup itself retired the old configuration; OR the gate only expects the most recent
   configuration per (tool, category) on the base ref. They differ in what you must preserve,
   so do NOT treat any of them as settled. The SAFE rule, satisfied by all three: across any
   setup migration keep `category` byte-identical AND retire the old producer, then verify on
   a throwaway probe PR before relying on it.
```

### WR-02: "an `analysis_key` change ALONE" is factually inaccurate, and generalising it beyond CodeQL risks wedging `main`

**File:** `AGENTS.md:279-290` (headline sentence) and `.github/workflows/codeql.yml:116`

**(a) It was not `analysis_key` alone.** `environment` changed too. Verbatim from the API,
same category `/language:actions`, same tool version 2.26.1:

```
id 1527111867 (default setup)
  analysis_key: dynamic/github-code-scanning/codeql:analyze
  environment:  {"build-mode":"none","category":"/language:actions","language":"actions","runner":"[\"ubuntu-latest\"]"}

id 1527170976 (advanced setup)
  analysis_key: .github/workflows/codeql.yml:analyze
  environment:  {"build-mode":"none","language":"actions"}
```

So of the `(analysis_key, category, environment)` tuple the text says the gate matches on,
**two of three components changed** and only `category` held. Writing "ALONE" states the
opposite of what the evidence shows, and it silently drops the one fact that most undermines
the tuple-matching model this same paragraph opens with. (If the gate really matched on the
full tuple, this migration would have orphaned -- and it did not. That tension is worth
stating out loud rather than papering over.)

**(b) The rule is written tool-agnostically from an n=1 CodeQL observation.** The bolded
sentence contains no scope qualifier. A future maintainer renaming `.github/workflows/ci.yml`
or its `code-scanning` job would change `analysis_key` from
`.github/workflows/ci.yml:code-scanning` for the **required** `angular-typechecker` tool,
read this line as proven-safe, and skip step 0. If mechanism 1 or 2 in WR-01 is the real one,
that is a permanent "1 configuration not found" block on an empty-bypass `main` -- the exact
worst case step 0 exists to prevent, and the hardest failure in this repo's history.

**Fix:** the WR-01 replacement text above already fixes (a) by naming `environment`. For (b),
append a scope sentence:

```markdown
   SCOPE: this was observed ONCE, for CodeQL, in a default -> advanced setup migration where
   the old producer was simultaneously disabled. It is NOT established for third-party tools:
   renaming `.github/workflows/ci.yml` or its `code-scanning` job would change `analysis_key`
   for the REQUIRED `angular-typechecker` tool with no "disable the old producer" signal
   available. Before any such rename, run step 0's orphan CHECK and verify on a throwaway
   probe PR.
```
