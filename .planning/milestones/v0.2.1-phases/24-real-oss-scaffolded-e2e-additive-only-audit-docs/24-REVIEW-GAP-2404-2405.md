## Summary

Adversarial review of the phase-24 gap-closure changeset (Plan 24-04 nx-dependency fix,
Plan 24-05 yarn/pnpm CLI e2e specs, plus a yarn docstring refinement). Cross-referenced
against the resolved debug doc (`.planning/debug/resolved/cli-yarn-e2e-wrong-version.md`),
the passing npm reference spec (`ng-add-ng-run.e2e.spec.ts`), the shared globalSetup, and
the `@workspace/test-util` helpers.

The core changes are correct:

- **`package.json`**: `nx` declared as a direct `^23.0.0` dependency (not a peer);
  `@nx/devkit` stays exact `23.0.1`. `^23.0.0` (`>=23.0.0 <24.0.0`) is a strict subset of
  `@nx/devkit@23.0.1`'s `nx` peer (`">= 22 <= 24 || ^23.0.0-0"`), so no double-constraint
  conflict, and it pins Nx-23-only support. This is a genuine product fix for the yarn UX
  gap (yarn does not auto-install the `@nx/devkit` peer that npm/pnpm add).
- **`package-manifest.spec.ts`**: the inverted guard (`toBe('^23.0.0')` +
  `not.toHaveProperty('nx')`) is non-vacuous; `peerDependencies` is a populated object so
  the negative property check is real.
- **`eslint.config.mjs`**: adding `nx` to `@nx/dependency-checks` `ignoredDependencies` is
  necessary (nx is declared but never imported by `src/`, so it would otherwise trip
  `obsoleteDependency` at `maxWarnings:0`); the comment is factually accurate.
- **Both e2e specs**: the Verdaccio `http://127.0.0.1:` SAFETY invariant is asserted in
  each test (and enforced by the globalSetup publish gate); no spec publishes to a public
  registry; `unsafeHttpWhitelist` is scoped to `127.0.0.1` only; leaf codes are DISTINCT
  full `TSxxxx` tokens (TS2322 / TS2345 / TS2554) with genuine cross-bleed `not.toContain`
  scoping; `it.skipIf` guards (`corepackAvailable` / `pnpmAvailable`) skip cleanly; the
  pnpm spec fails loudly on pnpm < 11; `execSync` targets are fixed constants (no command
  injection); and the prior TEMP-DIAGNOSTIC / atc-probe / console.log scaffolding is fully
  removed.
- **Yarn docstring**: accurately scopes the `ng-add`-no-autowire cause to *this package's*
  `@nx/devkit`-based factory (the `createSchematic('ng-add')` probe throwing while loading
  `convertNxGenerator`, swallowed by a bare `catch {}`), and explicitly states it is NOT
  asserted as a general Angular-CLI-under-yarn bug, naming the vanilla (Nx-free) schematic
  repro as a prerequisite for any upstream attribution. This matches the debug doc's
  post-24-05 root-cause pin. No over-claim.

No BLOCKER-severity defects. Two WARNING-level defects (a test-honesty gap and stale
instruction-file guidance that contradicts the new operative rule) and three INFO items.

## Warnings

### WR-01: Yarn CLI spec omits the library clean baseline (per-project scoping proof is weaker than its siblings)

**File:** `e2e/angular-typechecker-ng-cli-e2e/src/ng-add-ng-run-yarn.e2e.spec.ts:325-327`
**Issue:** The yarn spec runs a CLEAN baseline for the APP target only
(`appClean` -> exit 0), then plants errors. It never runs a clean baseline for the LIBRARY
target. Both sibling CLI specs DO check both: `ng-add-ng-run.e2e.spec.ts:229-232` and
`ng-add-ng-run-pnpm.e2e.spec.ts:290-293` each assert `appClean` AND `libClean` are green
before planting. Without a `libClean` assertion, the library-scoping proof rests solely on
`libBad` (exit non-zero + contains TS2554). That is still meaningful — TS2554 can only
appear if the planted `parseInt()` leaf was actually compiled — but a green pre-plant
baseline is what proves the library target was healthy to begin with (i.e. that the
non-zero exit is caused by the plant, not a pre-existing target misconfiguration). This is
an honesty/robustness asymmetry against the two specs it is meant to mirror.
**Fix:** Add a library clean baseline immediately after the app clean baseline, matching
the pnpm/npm specs:
```ts
// CLEAN baseline: each target type-checks the pristine scaffold GREEN.
const appClean = ngRun(tmp, `${APP_PROJECT}:typecheck`, npmEnv);
expect(appClean.code, appClean.stdout).toBe(0);
const libClean = ngRun(tmp, `${LIB_PROJECT}:typecheck`, npmEnv);
expect(libClean.code, libClean.stdout).toBe(0);
```

### WR-02: CLAUDE.md still contains three unannotated statements that contradict the new "nx is a direct dependency" rule

**File:** `CLAUDE.md:141`, `CLAUDE.md:176`, `CLAUDE.md:158`
**Issue:** The correction pass added a `[v0.2.1 CORRECTION ...]` annotation to four spots
(the Constraints line, the Headline-finding bullet, and the two Recommended-Stack rows) but
missed three others that now directly contradict the operative rule. Since CLAUDE.md drives
agent behavior in this repo (per the AGENTS.md instruction-accuracy discipline), a stale
"do not declare nx" statement can mis-steer a future agent into "fixing" `package.json` by
removing `nx` — undoing the yarn fix. The unannotated contradictions:
- **Line 141** (Installation block): `# (NO nx, NO @nx/plugin, NO vitest in the published
  package)` and line 137 `# dependencies: @nx/devkit@23.0.1, tslib@^2.3.0` — both omit/deny
  the now-declared `nx` dependency.
- **Line 176** (Version Compatibility table, `nx` row): `Not declared in the plugin's
  package.json.` — now factually false.
- **Line 158** (What NOT to Use table, `nx` row): the "Avoid" cell got the correction
  annotation, but the same row's **Why** cell still reads "Declaring it yourself causes
  double-constraint/skew" and the **Use Instead** cell still reads "Depend only on
  `@nx/devkit` (pinned); let its peer carry `nx`." — both still advocate the superseded
  approach with no correction.
**Fix:** Append the same `[v0.2.1 CORRECTION (2026-07-12): ...]` annotation (or rewrite) to
line 141, line 137, the line 176 note, and the line 158 Why/Use-Instead cells so every
nx-classification statement in CLAUDE.md is consistent with the operative Constraints line.

## Info

### IN-01: Non-ASCII em dash in the yarn spec test title violates the repo ASCII-only convention

**File:** `e2e/angular-typechecker-ng-cli-e2e/src/ng-add-ng-run-yarn.e2e.spec.ts:244`
**Issue:** The test title `'auto-wires every project and catches planted leaf errors — %s
layout'` contains a U+2014 em dash. The project convention (global CLAUDE.md) is ASCII-only
to avoid cp1252 mojibake in Windows console/reporter output; em dashes must be `--`. The
new pnpm spec correctly avoids this. Pre-existing (context line in the diff), but the file
is in review scope and this is the only non-ASCII character across the two specs.
**Fix:** Replace ` — ` with ` -- `:
```ts
'auto-wires every project and catches planted leaf errors -- %s layout',
```

### IN-02: Yarn spec test title says "auto-wires every project" although the whole point is that `ng add` does NOT auto-wire under yarn

**File:** `e2e/angular-typechecker-ng-cli-e2e/src/ng-add-ng-run-yarn.e2e.spec.ts:244` (with `describe` at :242)
**Issue:** The describe/it read together as "CLI-YARN: `ng add` + `ng run :typecheck` ... >
auto-wires every project ...". The spec's headline finding (and the assertions at :296-297)
is precisely that `ng add` INSTALLS-WITHOUT-WIRING under yarn, and the wiring is done by the
explicit `ng g angular-typechecker:ng-add` fallback. The title is technically defensible
(the `ng g` schematic does wire every project) but it can mislead a reader skimming test
names into thinking `ng add` auto-wires under yarn — the exact misconception the "lock the
quirk" assertion exists to prevent. Not a correctness defect; the assertions are honest.
**Fix:** Consider retitling to reflect the fallback, e.g.
`'ng add installs without wiring; ng g :ng-add wires every project and catches planted leaf errors -- %s layout'`.

### IN-03: nx-dependency assertion duplicated across two manifest-spec tests

**File:** `packages/angular-typechecker/src/package-manifest.spec.ts:85-88` and `:191-194`
**Issue:** The identical pair of assertions (`dependencies['nx'] === '^23.0.0'` and
`peerDependencies` has no `nx`) appears in two separate `it` blocks (the compatibility
contract and the Angular CLI install contract). Both are non-vacuous and each is
contextually reasonable, but the duplication is redundant maintenance surface — a future
range change must be edited in two places. Low priority.
**Fix:** Optional — keep one canonical assertion (the CMP-01 contract test at :85-88) and
drop the duplicate from the ACP-01 test, or leave as-is if the per-context coverage is
intentional.
