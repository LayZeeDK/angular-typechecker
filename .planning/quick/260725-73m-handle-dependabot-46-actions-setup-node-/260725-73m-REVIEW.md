### C2 -- item 6 retires a fork conclusion that is still true, and its fork evidence does not bear on forks

**Text (AGENTS.md:321-327):**

> 6. **Fork / Dependabot PRs -- the real mechanism (FIXED for Dependabot; inferred for
>    forks).** A read-only token does NOT suppress the SARIF upload: [...]
>    PROVEN in this repo -- Dependabot PR #46
>    is treated as a fork per GitHub's own Dependabot docs, yet its `ci.yml`
>    `code-scanning` job uploaded BOTH the `angular-typechecker` and `fallow` SARIF
>    successfully

**What is wrong -- two separable defects.**

**(a) #46 never exercised the fork path.** `gh api repos/.../pulls/46` returns
`head.repo.fork = false`, `head.repo.full_name = LayZeeDK/angular-typechecker`. Dependabot's
branch lives in THIS repo. GitHub's Dependabot doc scopes "treated as if they were opened from a
repository fork" to exactly two consequences and no more: "they receive a read-only
`GITHUB_TOKEN` and do not have access to any secrets". It does not set
`github.event.pull_request.head.repo.fork`. And `head.repo.fork` is the ONLY fork test this
repo's workflow applies. So the "yet ... treated as a fork" framing turns a NON-fork run into
proof about forks. What #46 actually proves is narrower and still worth keeping: a read-only
token alone does not suppress a `pull_request`-triggered SARIF upload.

**(b) Real fork PRs are still deterministically blocked, and by a cause the new text omits.**
`.github/workflows/ci.yml` gates both uploads on `fork == false`:

```
645:      - name: Upload angular-typechecker SARIF
646:        if: ${{ (github.event_name != 'pull_request' || github.event.pull_request.head.repo.fork == false) && steps.atc-sarif.outputs.produced == 'true' }}
654:      - name: Upload fallow SARIF
655:        if: ${{ (github.event_name != 'pull_request' || github.event.pull_request.head.repo.fork == false) && steps.fallow-sarif.outputs.produced == 'true' }}
```

with ci.yml's own comment at lines 520-522: "On a fork PR the GITHUB_TOKEN is read-only
regardless of the declared scope, so each upload step is gated to skip fork PRs -- the analysis
still RUNS on a fork PR, only the upload is skipped." `angular-typechecker` is a REQUIRED tool
of this gate. So on a real external fork PR there is provably no `angular-typechecker` analysis,
and GATE-02 still blocks -- regardless of what CodeQL does after the migration.

That makes the commit's premise wrong for the repo-specific half. Old item 6 said "A fork PR
gets a read-only token, so the upload steps skip -> no analysis -> the ruleset blocks it" and
"Un-path-gating the dogfood job cannot fix forks". Both are correct in OUTCOME -- the steps do
skip, by an explicit gate whose documented rationale in ci.yml is the read-only token. What was
wrong was only the implied GitHub-level mechanism (that GitHub would reject the upload). The new
text corrects the mechanism and discards the still-true conclusion, leaving a reader with
"forks probably work now".

**Second-order risk.** "A read-only token does NOT suppress the SARIF upload" reads as a standing
invitation to delete ci.yml's `fork == false` gates as dead weight. Nothing in this repo has
tested a genuine fork upload -- the gate guarantees the attempt is never made -- so that would be
a code change made on evidence that does not exist.

**Proposed replacement.** Retitle and append a paragraph before EVIDENCE BOUNDARY:

```
6. **Fork / Dependabot PRs -- the real mechanism (Dependabot FIXED by item 7's migration;
   real forks STILL BLOCKED).** A read-only token does NOT by itself suppress the SARIF
   upload: code scanning "always allows the uploading of results when the `pull_request`
   event triggers the action run" (GitHub Docs, code scanning troubleshooting). PROVEN in
   this repo for the TOKEN half -- Dependabot PR #46 runs with a read-only `GITHUB_TOKEN`
   (GitHub treats Dependabot-triggered runs "as if they were opened from a repository fork"
   for token and secret scoping), yet its `ci.yml` `code-scanning` job uploaded both the
   `angular-typechecker` and `fallow` SARIF (`refs/pull/46/merge`; angular-typechecker
   2026-07-25T02:58:33Z, fallow 02:58:39Z).
   [... default-setup / dynamic paragraph, per I2 ...]
   REAL EXTERNAL FORKS ARE A DIFFERENT CASE AND ARE STILL BLOCKED. #46 does not bear on
   them: `head.repo.fork` is FALSE for a Dependabot PR (the branch lives in this repo), so
   #46 took the NON-fork path. `ci.yml` gates both uploads on
   `github.event.pull_request.head.repo.fork == false` ("Upload angular-typechecker SARIF" /
   "Upload fallow SARIF"), so on a genuine fork PR the scan runs but nothing is uploaded and
   no `angular-typechecker` analysis exists -- and `angular-typechecker` is a REQUIRED tool
   of this gate. Whether GitHub would ACCEPT a fork-PR upload is untested here, because that
   gate prevents the attempt. So the standing answer for a real external contributor is
   unchanged: a maintainer-side re-run or the `enforcement: disabled` toggle. Do NOT remove
   ci.yml's fork gates on the strength of the #46 result.
```

### N1 (Suggestion) -- two residual causal "so" constructions, one directly under its own disclaimer

**`codeql.yml:17-18`:** "This workflow triggers on `pull_request`, which is inside the exemption,

**Fix (codeql.yml):** `- This workflow triggers on pull_request -- the event Actions DOES

### N2 (Important) -- the ordering constraint's trigger point is unstated, and it binds at PUSH time, not merge time

**Text (AGENTS.md:374-376):** "(a) the maintainer disables default setup BEFORE the advanced
workflow runs on the same ref (the categories are deliberately identical, so concurrent uploads
collide)".

`codeql.yml:41` is `pull_request: {}` -- unfiltered, no `branches:` list. So the advanced
workflow first runs the moment this branch is pushed and a PR is opened, NOT at merge. "Before
the advanced workflow runs on the same ref" is easy to read as "before it merges to `main`",
which would put the collision on the PR ref -- and the colliding checks are the two REQUIRED
contexts, on an empty-bypass `main`. GitHub's own switch procedure puts the disable first, before
the workflow is even committed: "**Switch to advanced** ... click **Disable CodeQL**", and only
then step 5 "edit the workflow". Here the workflow is already committed, so the disable must
happen before the PUSH. This is the very next action in this task, which is why it is Important
rather than a nit.

**Fix (append to item 7 (a)):** `Note WHEN that bites: codeql.yml triggers on an unfiltered
pull_request, so it first runs the instant the branch is PUSHED and a PR is opened -- not at
merge. Default setup must therefore be disabled BEFORE the push, not before the merge.
(GitHub's documented switch procedure disables CodeQL before the advanced workflow is even
committed; this repo committed it first, so the disable is the gate on pushing.)`
