<domain>
## Phase Boundary

Cut `angular-typechecker@0.0.2` and PROVE the tokenless OIDC steady-state publish
works end-to-end. This is the only unproven link in the release pipeline:

- 0.0.1 was published via a one-time granular SEED token (the first publish cannot
  use OIDC -- npm/cli#8544), then the npm Trusted Publisher (OIDC) was registered
  and the seed token revoked.
- The OIDC path is therefore REGISTERED but never EXERCISED. 0.0.2 is the first
  release that authenticates tokenlessly through the Trusted Publisher.

In scope: deriving + tagging 0.0.2, running the existing hardened `release.yml`
through a real OIDC publish, applying the documented registry-url fallback only if
it 404s, and verifying the result (version + provenance + dist-tag + GitHub Release).
ALSO in scope (added by maintainer during discuss): an `AGENTS.md` documenting how
Conventional Commits commit types drive the changelog and the semantic version (the
exact mechanic this phase exercised), referenced from `CLAUDE.md`.

Out of scope (own phases): the Release-PR workflow + branch-protection switch +
changelog systematization (Phase 7); the cross-OS / multi-Node CI matrix (Phase 6);
staged publishing (`npm stage publish`); any new executor/engine functionality.
</domain>

<decisions>
## Implementation Decisions

### Version derivation
- **D-01:** Pin the version EXPLICITLY: `npx nx release 0.0.2 --skip-publish` (local
  version bump + changelog + tag). Do NOT rely on `conventionalCommits` to compute
  the bump. VERIFIED against source: the 9 commits since `angular-typechecker@0.0.1`
  are all `docs(...)` / `chore(release)`, NONE touch `packages/angular-typechecker`,
  and there are ZERO `feat`/`fix` commits -- so `conventionalCommits` (with
  `release.projects: ["angular-typechecker"]`) detects no releasable change and bumps
  nothing. (The release-mechanics memory's "repo full of feat/fix dev commits ->
  auto-bumps to 0.0.2" describes the PRE-tag state and is now STALE for 0.0.2.)
- **D-02:** Use the CURRENT release flow, NOT Phase 7's Release-PR flow: cut version +
  changelog + tag locally (`--skip-publish`), push the tag `angular-typechecker@0.0.2`,
  which fires `release.yml`; CI runs `nx release publish`. Phase 7 explicitly owns the
  switch to Release-PR + branch protection -- do not pre-adopt it here.

### OIDC publish contingency (the empty-_authToken trap)
- **D-03:** Attempt the publish with `release.yml` AS-IS. The current workflow is
  already the documented WORKING OIDC config: `node-version: 24` + `npm i -g npm@latest`
  (=> npm >= 11.5.1, the version trusted publishing requires), `registry-url` set, NO
  `NODE_AUTH_TOKEN` env block, job-scoped `id-token: write`, `NPM_CONFIG_PROVENANCE: true`,
  exact-match Trusted Publisher (repo `LayZeeDK/angular-typechecker`, workflow
  `release.yml`, env `npm-publish`).
- **D-04:** REACTIVE fallback ONLY: if the OIDC publish 404s on auth, drop `registry-url`
  from the `setup-node` step (the empty-`_authToken` trap: setup-node writes an
  `.npmrc` referencing `${NODE_AUTH_TOKEN}`; unset -> empty `_authToken=` which npm may
  try to use instead of falling back to OIDC), then re-run. A 404-on-auth means the
  package was NOT published, so re-attempting the same 0.0.2 is safe. Do NOT proactively
  drop `registry-url` -- the whole point of this phase is to verify whether the current
  config works; the inline `release.yml` comment + ROADMAP prescribe the reactive drop.
- **D-05:** Research-backed pre-flight: the #1 cause of the misleading OIDC 404 is npm
  < 11.5.1 / Node < 22.14 -- already mitigated. The #2 cause is exact-match config
  drift (repo casing, workflow filename, `repository.url`) -- already correct from 05-05
  (`repository.url` = `git+https://github.com/LayZeeDK/angular-typechecker.git`). Re-confirm
  both as a quick pre-publish check before tagging.

### Release payload + public changelog
- **D-06:** Hand-curate the public 0.0.2 changelog entry (CHANGELOG.md + GitHub Release
  notes) in the same clean style as the 0.0.1 entry -- NO GSD plan-id scopes. The
  auto-generated changelog would be empty or leak `docs(05):`-style scopes (only
  docs/chore commits exist since the tag). Phase 7 systematizes this; 5.1 curates
  manually as the interim.
- **D-07:** Recommended default for the payload: 0.0.2 is a maintenance / verification
  release with NO functional source change (its purpose is to exercise OIDC). See
  Open Question OQ-1 -- this is FLAGGED for maintainer confirmation at the human gate,
  not silently locked.

### Verification / done criteria
- **D-08:** Success = `npm view angular-typechecker@0.0.2 --json` shows `version: 0.0.2`
  AND `dist.attestations.provenance.predicateType: https://slsa.dev/provenance/v1`
  (SLSA provenance present), `dist-tags.latest: 0.0.2`, published via OIDC (the CI run
  carried NO seed token / NODE_AUTH_TOKEN), and a GitHub Release `angular-typechecker@0.0.2`
  with curated notes exists.
- **D-09:** Regression guard: confirm `release.yml` stays OIDC-only (no active
  `NODE_AUTH_TOKEN`, no re-added seed line) and the `NPM_SEED_TOKEN` GitHub secret
  remains deleted; the `release-hygiene` integration spec (auth-token-unset assertion)
  stays green.

### Documentation deliverable -- AGENTS.md (IMPLEMENTED during discuss)
- **D-11:** Create `AGENTS.md` (repo root) documenting Conventional Commits commit types

### Human-gating

<specifics>
## Specific Ideas

- The verification crux (what 0.0.2 actually tests): does `setup-node`'s `registry-url`
  inject an empty `_authToken` into `.npmrc` that defeats the OIDC fallback when
  `NODE_AUTH_TOKEN` is unset? Documented reactive fix: drop `registry-url`. Web research
  (npm Docs trusted-publishers; npm/cli#9088 misleading-404; GitHub OIDC GA changelog;
  multiple 2025/2026 CI postmortems) indicates modern npm (>= 11.5.1) + no explicit token
  handles `registry-url` correctly, so the as-is attempt SHOULD succeed -- but this phase
  exists precisely to confirm that empirically on this repo's Trusted Publisher.
- Re-confirm before tagging: npm version in the CI run will be >= 11.5.1 (Node 24 + the
  `npm i -g npm@latest` step), and the Trusted Publisher exact-match fields are unchanged.

</specifics>
