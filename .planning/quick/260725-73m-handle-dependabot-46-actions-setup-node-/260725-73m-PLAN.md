# Quick Task 260725-73m: setup-node v7 pin + CodeQL advanced setup

## Context

Dependabot PR #46 (`actions/setup-node` 6.4.0 -> 7.0.0) is permanently `BLOCKED`. Its `ci`
check is SUCCESS with 24 other green checks, but the two required contexts
`Analyze (actions)` and `Analyze (javascript-typescript)` **do not exist** on the PR at all.
Controlled comparison (RESEARCH section 1): maintainer PRs #64/#65 get both checks;
Dependabot PRs #46/#59 get neither, because CodeQL **default setup** runs as event
`dynamic` — outside the `pull_request` upload exemption — and GitHub never schedules that
run on a Dependabot-triggered ref.

The fix is CodeQL **advanced setup**, whose official template triggers on `pull_request`.
Corroborated in the opposite direction inside this repo: `ci.yml`'s `code-scanning` job runs
on `pull_request` and DID upload both SARIFs on PR #46 (`refs/pull/46/merge`,
2026-07-25T02:58:33Z) despite the read-only Dependabot token.

All findings are already verified in `260725-73m-RESEARCH.md`. Do not re-research.

## Human-gated runbook (the executor MUST NOT perform any of this)

Every step here is either a repository security-configuration change on the gate guarding
`main` or an irreversible Code Scanning API deletion. AGENTS.md reserves both classes for the
maintainer. The executor's job ends at a committed branch.

### Why the ordering matters: the orphaned-config hazard

Migrating default -> advanced changes `analysis_key` from
`dynamic/github-code-scanning/codeql:analyze` to `.github/workflows/codeql.yml:analyze`
while `category` stays `/language:actions` / `/language:javascript-typescript`. The
"Require code scanning results" rule matches a required tool by its
`(analysis_key, category, environment)` tuple, so the moment default setup is disabled its
config on `main` becomes ORPHANED — a tuple the gate still expects that no future upload can
reproduce. Per the GATE-02 runbook, "configuration not found" is TRANSIENT for a live config
but PERMANENT for an orphaned one, so an orphan blocks EVERY PR until its analyses are
deleted. This is the exact failure spike 012 diagnosed.

Second hazard: `codeql.yml`'s category is deliberately identical to default setup's, so if
both configurations run on the same ref the uploads collide. GitHub's documented switch
procedure disables default setup FIRST.

### Recommended ordering (minimum exposure)

1. **Relax only the CodeQL leg.** In the `main` ruleset's "Require code scanning results"
   rule, temporarily REMOVE `CodeQL` from the required-tools list, leaving
   `angular-typechecker` required. The branch ruleset's required status-check contexts
   (`Analyze (actions)`, `Analyze (javascript-typescript)`, `ci`) stay required and are
   unaffected — the migration does not change those names, so `codeql.yml` satisfies them.
   Exposure: the CodeQL Code-Scanning-results leg only, for the length of the migration.
2. **Disable CodeQL default setup** (Security -> Code scanning -> CodeQL analysis row ->
   "Switch to advanced" -> "Disable CodeQL"). Do this BEFORE the migration PR's CodeQL run,
   so the two configurations never upload the same category on the same ref.
3. **Push the branch and open the PR.** Confirm `ci` is green and that `Analyze (actions)` +
   `Analyze (javascript-typescript)` appear and are green — this is the first real proof the
   check names render byte-exactly.
4. **Merge as a merge commit** (the repo's only allowed merge method). The push-to-`main`
   run of `codeql.yml` then produces the FIRST advanced-setup analyses on `main`, with the
   new `analysis_key` and the same categories.
5. **Delete the orphaned default-setup analyses** — only now, so a live advanced-setup config
   already exists on `main` and CodeQL is never "not configured":
   `GET /repos/LayZeeDK/angular-typechecker/code-scanning/analyses?tool_name=CodeQL&ref=refs/heads/main`,
   identify entries whose `analysis_key` is `dynamic/github-code-scanning/codeql:analyze`,
   then `DELETE /repos/LayZeeDK/angular-typechecker/code-scanning/analyses/{id}` for each,
   following each response's `next_analysis_url` for ordering. The LAST analysis in a set
   returns HTTP 400 unless you pass `?confirm_delete=true`.
6. **Re-add `CodeQL` to the required-tools list** with the same conservative threshold it had
   (`errors` / `high_or_higher`), restoring full enforcement.
7. **Verify** on a throwaway probe PR (ideally one planning-only and one code PR, mirroring
   the step-3 probes the original GATE-02 rollout used): both `Analyze (*)` checks report, no
   "configuration not found" warning, merge button not blocked. Then verify the actual goal
   on a Dependabot PR (e.g. re-run or reopen #59): the `Analyze (*)` checks should now appear.
8. **Close Dependabot PR #46** with a comment that the bump was applied by hand in this PR.

### Alternative orderings and their exposure

- **No ruleset relaxation; disable default setup, then open the PR.** The migration PR itself
  is evaluated against the freshly-orphaned default-setup config -> "configuration not found"
  -> permanently blocked, and the orphan cannot be cleaned cleanly until an advanced-setup
  analysis exists on `main`, which requires the merge. Likely deadlock; you end up relaxing
  the ruleset anyway, under pressure. NOT recommended.
- **Open the PR first, disable default setup later.** Both configurations upload
  `/language:*` on the same ref -> category collision -> the PR's `Analyze (*)` jobs can go
  red. Recoverable (disable, then re-run) but noisy. NOT recommended.
- **Whole-ruleset toggle (`enforcement: disabled`) instead of step 1.** This is the
  AGENTS.md-documented recovery and it works, but it relaxes `ci` and branch protection too.
  Prefer the surgical step 1; keep this as the fallback.

`enforcement: active` — exactly as AGENTS.md "Lockout recovery". NEVER add a standing bypass
actor.
