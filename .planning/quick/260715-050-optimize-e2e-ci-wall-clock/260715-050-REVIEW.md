### IN-01: `discover` step assumes single-line JSON and swallows a discovery failure

**File:** `.github/workflows/ci.yml:171-172`

**Issue:** `run: echo "projects=$(npx nx show projects --with-target e2e --json)" >> "$GITHUB_OUTPUT"`
relies on `nx show projects --json` emitting single-line JSON (it does today), and
on the substitution not failing. Two edge cases:
1. If a future nx ever pretty-prints or leaks a stdout line, the `key=value`
   `$GITHUB_OUTPUT` write malforms and `fromJSON(...)` errors -- this fails LOUD
   (the e2e job fails), not silently, and the executor's imminent CI run would catch
   it. Low risk.
2. Under the default `bash -eo pipefail` shell, a FAILING `nx show projects` inside
   `$(...)` does not trip `set -e` (the enclosing `echo` exits 0), so a discovery
   failure yields `projects=` (empty) -> the e2e matrix falls back to the 4 known
   projects. Today that is a lossless fallback, but a future 5th e2e project would be
   silently dropped from CI if discovery ever broke.

**Fix (optional hardening):** Use the block form so a discovery failure fails the
build job and multi-line output cannot corrupt the write:
```yaml
- id: discover
  run: |
    projects="$(npx nx show projects --with-target e2e --json)"
    echo "projects=$projects" >> "$GITHUB_OUTPUT"
```
Not required for this run (fallback + single-line JSON make it safe today).

### IN-02: `${{ matrix.project }}` is interpolated into run steps, but it is not PR-metadata and the trust context is safe

**File:** `.github/workflows/ci.yml:257, 264`

**Issue:** The plan's threat model claims "no PR-metadata interpolation into run
steps." `${{ matrix.project }}` IS interpolated into two `run:` shell commands. Its
value comes from the trusted `build`-job output (nx-discovered project names) or the
fixed 4-name fallback -- never from PR title/branch/author. On a fork PR the project
names are technically PR-controlled content, so a maliciously-named project could in
principle inject into the shell; however this workflow uses the SAFE `pull_request`
trigger with `contents: read` and no secrets, so any such execution runs in the same
untrusted-PR sandbox that already runs the PR's own e2e vitest specs (arbitrary code
by design). No privilege escalation, no secret exposure. The posture claim is
therefore essentially correct.

**Fix:** None required. If defense-in-depth is ever wanted, pass the value via an
intermediate `env:` var rather than direct `${{ }}` interpolation -- gold-plating
given the trust context.
