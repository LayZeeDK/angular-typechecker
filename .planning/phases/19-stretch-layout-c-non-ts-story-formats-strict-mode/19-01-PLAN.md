<objective>
Ship the ONE board-blessed SB-08 stretch item: an opt-in `strict` mode (default false) that escalates
the existing coverage-incomplete outcome from non-clean-but-passing to a HARD FAIL for a dropped
in-graph WARNING. This is D-01, additive, pure-core, and a thin escalation on top of the SB-04 split
counter + coverage-incomplete outcome already shipped in Phase 17.

RATIFY assumption A1 (19-RESEARCH.md): the ONLY case `strict` changes is a dropped in-graph WARNING
with `maxWarnings` unset -- which today passes CLEAN (evaluate-result.ts:124-129; asserted at
evaluate-result.spec.ts:143). The dropped in-graph ERROR case ALREADY hard-fails by default
(evaluate-result.ts:97) and strict does NOT change it. Therefore the criterion-2 negative test that
demonstrates the FLIP MUST use a dropped in-graph WARNING, never an error. The LOCKED strict semantics
("FAIL on suppressedInGraph > 0, default off, threaded through evaluateResult") are fully satisfied by
this one-gate edit; do NOT add strict to CoreOptions/runTypecheck or exit-codes.ts (both are dead
plumbing for it -- see the anti-patterns in 19-RESEARCH.md).

Purpose: give CI/agent loops a way to treat any coverage loss (a dropped first-party diagnostic) as a
build failure, not just an advisory -- consistent with the charter (over-report is the safe direction).

Output: `strict` surfaced in the three coupled option files + the pure verdict gate + full unit
coverage (the FLIP + the error-case regression guard + the schema-parity + the plumbing).
</objective>
