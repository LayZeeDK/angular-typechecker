## Warnings

### WR-01: AGENTS.md gotcha #3 LANDMINE mis-states nx 23.0.1 behavior (hard error, not a silent push)

**File:** `AGENTS.md:136-143`
**Issue:** The LANDMINE claims that re-enabling `changelog.workspaceChangelog.createRelease: "github"` while keeping `release.git.push: false` would cause nx to "**silently push** the version commit + tag during the local `nx release` step -- BEFORE you curate the changelog -- even with `--skip-publish`."

That is not how the installed `nx@23.0.1` behaves. In
`node_modules/nx/dist/src/command-line/release/config/config.js` (lines 136-149), nx
detects exactly this combination -- `git.push === false` (or the changelog/version-scoped
`git.push: false`) together with an enabled `createRelease` -- and returns the config error
`GIT_PUSH_FALSE_WITH_CREATE_RELEASE`, which is then surfaced (lines 899-909) with the
message "The createRelease option for changelogs cannot be enabled when git push is
explicitly disabled because the commit needs to be pushed to the remote in order to tie the
release to it" followed by `process.exit(1)`. So the dangerous config the doc warns about
is now **rejected outright** -- nx will refuse to run, not silently push.

The genuine silent-push hazard the postmortem describes only occurs when `git.push` is left
at its **default** (not explicitly `false`) while `createRelease` is enabled: at lines
154-159 the changelog git defaults flip `push` to `true` whenever `createRelease` is
enabled. That is the real "createRelease forces a push" mechanism, and it is invisible
precisely because the user never wrote `push: true`.

The current repo config (`git.push: false` + `createRelease: false`) is correct and safe
either way. But the rationale in the doc is wrong about the failure mode, which matters
because the file's own "Changing this file" policy (AGENTS.md:6-17) demands factual accuracy
against the actual tooling, and the example it cites (a release-mechanics claim that was
"once wrong about the 0.x semver bump shift and about `--skip-publish` semantics") is exactly
this class of defect.

**Fix:** Reword the LANDMINE to reflect nx 23.0.1's two distinct behaviors. Suggested:

```markdown
   **LANDMINE -- do NOT re-enable `changelog.workspaceChangelog.createRelease: "github"`.**
   In nx 23, an enabled `createRelease` and `git push` interact two ways, both of which
   defeat the curate-before-push flow:
   - If you re-enable `createRelease: "github"` while LEAVING `release.git.push: false`,
     nx now refuses to run: config validation throws
     `GIT_PUSH_FALSE_WITH_CREATE_RELEASE` ("createRelease ... cannot be enabled when git
     push is explicitly disabled ...") and exits non-zero (verified in nx 23.0.1
     `config.js`). The release simply will not cut.
   - If you re-enable `createRelease: "github"` AND drop the explicit `git.push: false`,
     nx silently defaults the changelog git `push` to `true` (it must push the tag to tie
     the GitHub Release to it -- verified in nx 23.0.1 `config.js`), so the version commit
     + tag are pushed during the local `nx release` step -- BEFORE you curate the
     changelog -- even with `--skip-publish` (which only skips the npm publish, not the git
     push). That race once pushed an un-curated commit + tag to a force-push-protected
     `main`, which could not be cleanly undone.

   `release.git.push: false` + `createRelease: false` is the fix; curation now always
   precedes the push.
```
